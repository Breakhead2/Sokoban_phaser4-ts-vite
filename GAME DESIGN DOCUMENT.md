# GAME DESIGN DOCUMENT

# Temple of the Last Seal

**Рабочее русское название:** «Храм последней печати»

**Версия документа:** 1.0

---

# 1. Общая информация

**Жанр:** Sokoban / логическая головоломка  
**Поджанр:** Puzzle Adventure  
**Платформа:** Web  
**Основной стек:** Phaser + Vite + TypeScript  
**Камера:** вид сверху  
**Количество уровней:** 10  
**Основная ориентация:** Landscape  
**Базовое разрешение:** 1280×720 px  
**Соотношение сторон:** 16:9  
**Предполагаемая продолжительность:** 20–40 минут

Игра создаётся как небольшой законченный проект, на котором можно освоить основные принципы разработки игр на Phaser:

- работу со сценами;
- tile-based движение;
- обработку ввода;
- загрузку уровней;
- состояние игры;
- UI;
- адаптацию под разные экраны;
- сохранение прогресса;
- звук;
- простые анимации.

Главный принцип разработки:

> Новые уровни должны требовать новых решений от игрока, а не постоянного создания новых программных систем.

---

# 2. Концепция

Искатель древностей обнаруживает вход в забытый подземный храм неизвестной цивилизации.

После проникновения внутрь он активирует древний механизм. Вход за его спиной закрывается.

Единственный путь — двигаться глубже.

Каждая комната храма представляет собой механизм, который активируется после установки каменных блоков на специальные ритуальные плиты.

Герой предполагает, что таким образом открывает путь к выходу.

Но постепенно становится понятно:

**каждая решённая головоломка снимает одну из древних печатей.**

Создатели храма построили его не для защиты сокровища от людей.

Они пытались удержать что-то внутри.

На десятом уровне игрок активирует последнюю печать.

---

# 3. Игровая фантазия

Игрок должен чувствовать себя исследователем, который самостоятельно проникает всё глубже в место, куда ему не следовало заходить.

Начало игры должно создавать ощущение:

**«Я исследую древние руины».**

Середина:

**«Здесь что-то не так».**

Финал:

**«Я всё это время делал именно то, чего нельзя было делать».**

Сюжет не должен мешать головоломкам.

Он существует как дополнительная награда за продвижение.

---

# 4. Основная механика

В основе игры лежит классический Sokoban.

Игрок перемещается по клеточной сетке.

Он может двигаться:

- вверх;
- вниз;
- влево;
- вправо.

Диагонального движения нет.

Игрок может толкать каменные блоки.

Блоки нельзя тянуть.

Одновременно можно толкнуть только один блок.

Если за блоком находится:

- стена;
- другой блок;
- непроходимый объект,

толкнуть его невозможно.

Для завершения уровня необходимо установить все каменные блоки на соответствующие ритуальные плиты.

# 6. Основной игровой цикл

Игрок входит в новый зал.

↓

Осматривает расположение блоков и плит.

↓

Продумывает последовательность действий.

↓

Передвигается по клеткам.

↓

Толкает каменные блоки.

↓

При необходимости использует Undo.

↓

Если решение оказалось неудачным — Restart.

↓

Все блоки установлены на ритуальные плиты.

↓

Активируется механизм.

↓

Открывается дверь.

↓

Игрок переходит на следующий уровень.

↓

Появляется новый фрагмент истории.

# 7. Базовое разрешение

## 7.1. Логическое разрешение

Базовое игровое разрешение:

**1280×720 px**

Соотношение сторон:

**16:9**

Ориентация:

**Landscape**

Именно относительно пространства 1280×720 проектируются:

- сцены;
- положение игрового поля;
- UI;
- меню;
- экран выбора уровней;
- сюжетные экраны;
- расположение мобильных элементов управления.

Реальное устройство пользователя может иметь другое разрешение.

Phaser масштабирует Canvas под доступную область экрана.

---

# 8. Масштабирование

Предполагаемая конфигурация Phaser:

```ts
scale: {
    mode: Phaser.Scale.FIT,
    autoCenter: Phaser.Scale.CENTER_BOTH,
    width: 1280,
    height: 720
}
```

`FIT` используется для сохранения пропорций игрового пространства.

`CENTER_BOTH` центрирует Canvas.

Основная игровая логика не зависит от физического разрешения устройства.

---

# 9. Safe Area

Не рекомендуется располагать критически важные элементы непосредственно возле края Canvas.

Необходимо предусмотреть внутреннюю безопасную область.

Ориентировочный минимальный отступ:

**24–32 px от края базового Canvas.**

Особенно это важно для мобильных устройств, где часть экрана может занимать:

- системная панель;
- вырез;
- закругление дисплея;
- браузерный интерфейс.

Основные UI-элементы должны находиться внутри Safe Area.

---

# 10. Размер тайла

Точный размер тайла определяется после окончательного выбора графического tileset.

Предварительные варианты:

**32×32 px**

или

**48×48 px**

Размер не следует выбирать независимо от ассетов.

Если tileset создан для 32×32, игра должна использовать его нативный размер либо кратное ему масштабирование.

Главное условие:

**весь игровой мир работает на одной клеточной сетке.**

---

# 11. Размер игровых карт

Карты всех десяти уровней должны быть относительно компактными.

Предварительный ориентир:

**до 16–18 клеток по горизонтали**

и

**до 10–12 клеток по вертикали.**

Это не жёсткое техническое ограничение, а дизайн-ориентир.

Карта должна полностью помещаться на игровом экране.

Игрок не должен:

- прокручивать карту;
- двигать камеру;
- терять из вида часть головоломки.

Для Sokoban важно видеть всю ситуацию целиком.

---

# 12. Размещение игрового поля

На ПК поле располагается примерно по центру экрана.

На смартфонах оно немного смещается к центру относительно зон управления.

Условная структура:

```text
┌──────────────────────────────────────────────────────┐
│ LEVEL 04                 MOVES 32               ☰    │
│                                                      │
│             ┌────────────────────────┐               │
│             │                        │               │
│             │                        │               │
│             │      GAME FIELD        │               │
│             │                        │               │
│             │                        │               │
│             └────────────────────────┘               │
│                                                      │
└──────────────────────────────────────────────────────┘
```

Игровое поле является главным визуальным элементом.

---

# 13. Ориентация устройства

Игра рассчитана исключительно на:

**горизонтальное расположение экрана.**

Landscape используется:

- на смартфонах;
- на планшетах;
- на десктопных устройствах.

Полноценная portrait-компоновка не создаётся.

Это позволяет:

- сохранить крупное игровое поле;
- разместить управление по бокам;
- использовать единую структуру UI;
- не разрабатывать две независимые версии интерфейса.

---

# 14. Неверная ориентация

Если мобильное устройство находится в вертикальном положении, игровой экран временно скрывается.

Поверх игры отображается специальный overlay.

Текст:

**Поверните устройство**

Для игры используйте горизонтальную ориентацию.

Также отображается:

- изображение смартфона;
- либо простая анимация его поворота.

Пример:

```text
┌───────────────────────┐
│                       │
│         📱 ↻           │
│                       │
│ Поверните устройство  │
│                       │
│ Для игры используйте  │
│ горизонтальный режим  │
│                       │
└───────────────────────┘
```

---

# 15. Поведение игры во время неправильной ориентации

При переходе в portrait:

- игровой ввод отключается;
- состояние уровня сохраняется;
- персонаж остаётся на текущей клетке;
- блоки остаются на текущих позициях;
- уровень не перезапускается.

После возвращения в landscape:

- overlay автоматически скрывается;
- управление снова включается;
- игра продолжается с текущего состояния.

---

# 16. Техническая реализация Orientation Overlay

Orientation Overlay желательно реализовать поверх Canvas.

Структура:

```text
HTML
│
├── Game Container
│      │
│      └── Phaser Canvas
│
└── Orientation Overlay
       ├── Rotate Icon
       ├── Заголовок
       └── Подсказка
```

Условие:

```text
width < height
```

на мобильном устройстве:

```text
Overlay = visible
Game Input = disabled
```

При:

```text
width >= height
```

:

```text
Overlay = hidden
Game Input = enabled
```

# 17. Управление на ПК

Основное управление:

**W / ↑** — вверх

**S / ↓** — вниз

**A / ←** — влево

**D / →** — вправо

Дополнительные действия:

**Z** — Undo

**R** — Restart

**Esc** — Pause

Допускается также использование UI-кнопок Undo и Restart мышью.

---

# 18. Управление на мобильных устройствах

Основной вариант:

**виртуальный D-pad.**

Дополнительный:

**свайпы.**

---

# 19. D-pad

В левой части экрана располагаются четыре кнопки направления.

```text
        ▲

    ◀       ▶

        ▼
```

Каждое короткое нажатие:

**один игровой ход.**

Это важно для Sokoban, поскольку управление должно быть максимально точным.

---

# 20. Размещение мобильного интерфейса

Основная схема:

```text
┌──────────────────────────────────────────────────────┐
│ LEVEL 04                 MOVES 32              ☰     │
│                                                      │
│                ┌────────────────────┐                │
│       ▲        │                    │        ↶       │
│     ◀   ▶      │     GAME FIELD     │                │
│       ▼        │                    │        ↻       │
│                └────────────────────┘                │
│                                                      │
└──────────────────────────────────────────────────────┘
```

Слева:

**D-pad**

Справа:

**Undo**

**Restart**

Сверху:

- номер уровня;
- количество ходов;
- Pause/Menu.

По центру:

**игровое поле.**

---

# 21. Размер сенсорных кнопок

Визуальная иконка и зона нажатия — не одно и то же.

Зона касания должна быть достаточно большой для управления большим пальцем.

Между соседними кнопками необходимо оставлять пространство, чтобы избежать случайных нажатий.

Особенно важно для:

- D-pad;
- Undo;
- Restart.

---

# 22. Swipe-управление

Дополнительно игрок может выполнять свайпы по игровому полю.

Свайп вверх:

**один шаг вверх.**

Свайп вниз:

**один шаг вниз.**

Свайп влево:

**один шаг влево.**

Свайп вправо:

**один шаг вправо.**

Свайп не должен автоматически перемещать персонажа до стены.

Один жест:

**один ход.**

---

# 23. Приоритет мобильного управления

Основной:

**D-pad**

Дополнительный:

**Swipe**

Не следует делать мобильную версию исключительно на свайпах.

Sokoban требует большого количества точных одиночных перемещений.

---

# 24. Удерживание направления

Для первой версии:

**не обязательно.**

Обычное касание всегда означает один шаг.

После завершения основной игры можно добавить:

удержание направления → последовательное движение с небольшой задержкой между шагами.

При этом движение всё равно остаётся дискретным.

---

# 25. Tap-to-move

Автоматическое перемещение персонажа после нажатия на клетку:

**не входит в MVP.**

Причина — необходимость реализации:

- поиска пути;
- проверки маршрута;
- поведения возле блоков;
- защиты от случайного толкания.

Для первой игры это лишнее усложнение.

---

# 26. Единая система Input

Игровая логика не должна напрямую зависеть от клавиатуры или D-pad.

Внутри игры существуют команды:

```text
UP
DOWN
LEFT
RIGHT
UNDO
RESTART
PAUSE
```

Источники ввода преобразуются в эти команды.

Например:

```text
Keyboard ArrowLeft
        │
Keyboard A
        │
D-pad ◀ ├─── LEFT ─── MovementSystem
        │
Swipe ←
```

Таким образом, механика движения пишется один раз.

---

# 27. Игрок

Главный персонаж:

**искатель древностей / археолог / авантюрист.**

Для первой версии достаточно следующих анимаций:

- idle вниз;
- idle вверх;
- idle влево;
- idle вправо;
- ходьба вниз;
- ходьба вверх;
- ходьба влево;
- ходьба вправо.

Возможен упрощённый вариант:

одна idle-поза + четыре направления ходьбы.

---

# 28. Каменный блок

Главный игровой объект.

Игрок может толкнуть его на соседнюю клетку.

Блок нельзя:

- тянуть;
- двигать через стену;
- толкать вместе с другим блоком;
- толкать за пределы уровня.

При перемещении желательно воспроизводить:

- короткую анимацию;
- звук тяжёлого камня.

---

# 29. Ритуальная плита

Целевая клетка для блока.

Состояния:

**Inactive**

и

**Active**

При установке блока на плиту:

- меняется спрайт;
- появляется небольшое свечение;
- воспроизводится звук;
- возможно краткое появление частиц.

Если блок убирается:

плита снова становится неактивной.

---

# 30. Каменная дверь

В начале уровня:

**закрыта.**

После активации всех плит:

- запускается механизм;
- дверь открывается;
- появляется доступ к выходу.

Переход на следующий уровень происходит после того, как герой входит в открытую дверь.

---

# 31. Undo

Undo входит в основную версию игры.

Перед каждым игровым действием необходимо сохранять:

- позицию игрока;
- положение всех блоков.

При Undo восстанавливается предыдущее состояние.

Игрок может использовать Undo несколько раз подряд.

---

# 32. Restart

Restart полностью возвращает уровень к первоначальному состоянию.

На ПК:

клавиша R или кнопка.

На мобильном:

кнопка ↻.

Для защиты от случайного нажатия желательно показать подтверждение:

**Начать уровень заново?**

[Да]

[Нет]

---

# 33. Счётчик ходов

Во время уровня отображается:

**Ходы: 32**

Ходом считается успешное перемещение игрока на одну клетку.

Счётчик нужен для:

- обратной связи;
- повторного прохождения;
- будущей системы рекордов.

---

# 34. Условие победы

Уровень считается решённым, когда:

**каждая ритуальная плита занята каменным блоком.**

После этого:

1. блокируется кратковременный ввод;
2. активируются все плиты;
3. запускается звук механизма;
4. открывается дверь;
5. ввод возвращается;
6. игрок входит в выход.

---

# 35. Структура уровней

Всего:

**10 уровней.**

Каждый является отдельным помещением храма.

Сложность увеличивается постепенно.

Новые уровни прежде всего усложняют:

- расположение блоков;
- расположение плит;
- узкие проходы;
- порядок действий;
- потенциальные тупики.

---

# 36. Уровень 1 — Вход

Цель:

обучить игрока базовому движению.

Количество:

**1 блок**

**1 плита**

Практически невозможно проиграть.

Игрок понимает:

- как ходить;
- как толкать блок;
- куда его нужно поставить.

После решения:

плита загорается.

Дверь открывается.

Текст:

> Где-то глубоко под храмом раздаётся глухой удар.

---

# 37. Уровень 2 — Первая печать

Количество:

**2 блока**

**2 плиты**

Впервые важен порядок действий.

Над выходом расположен необычный символ.

После прохождения он начинает светиться.

---

# 38. Уровень 3 — Зал колонн

Появляются:

- колонны;
- более узкие проходы;
- реальные тупики.

Игрок впервые может неправильно поставить блок и быть вынужден использовать Undo или Restart.

На стене находится изображение людей, закрывающих массивные врата.

---

# 39. Уровень 4 — Зал стражей

Декорации:

- статуи;
- щиты;
- древние символы.

Сложность создаётся компактной планировкой.

После прохождения:

> Эти изображения похожи не на молитву.

---

# 40. Уровень 5 — Святилище

Визуально отличается от предыдущих помещений.

Появляются:

- золотые детали;
- светящиеся руны;
- более сложные ритуальные плиты.

После решения где-то глубже запускается большой механизм.

---

# 41. Уровень 6 — Предупреждение

На стене находится повреждённая надпись:

> НЕ ОТКРЫВАТЬ  
> НЕ БУДИТЬ  
> НЕ...

# 62. Представление уровня

Игровая логика должна работать с клетками, а не с физическими координатами Phaser.

Пример:

```text
########
#......#
#..B...#
#......#
#..P...#
#...G..#
########
```

Обозначения:

`#` — стена

`.` — пол

`B` — блок

`P` — плита

`G` — игрок

Рендер превращает логические клетки в графические объекты.

---

# 63. Важный технический принцип

Для Sokoban не следует строить основную механику на Phaser Arcade Physics.

Лучше использовать:

**дискретную игровую сетку.**

Например:

```ts
player.gridX
player.gridY
```

При попытке движения:

1. вычисляется соседняя клетка;
2. проверяется стена;
3. проверяется наличие блока;
4. при необходимости проверяется клетка за блоком;
5. обновляется игровое состояние;
6. затем запускается визуальная анимация перемещения.

Таким образом:

**логика определяет визуал, а не наоборот.**

---

# 64. Анимация движения

Логически игрок перемещается:

**из одной клетки в другую.**

Визуально можно добавить короткий tween.

Например:

**100–150 мс.**

Это создаёт плавность, но не превращает движение в физическое.

То же относится к блокам.

# 80. Главный принцип проекта

Первая цель проекта — не создать максимально большую игру.

Цель:

**самостоятельно пройти полный цикл разработки небольшой законченной игры.**

Поэтому любое новое предложение оценивается вопросом:

> Делает ли это наши 10 уровней заметно лучше?

Если нет — функцию следует оставить для следующего проекта или версии 2.0.

Базовая формула Temple of the Last Seal остаётся простой:

**ходи → толкай → думай → активируй печать → спускайся глубже → узнай, что ты натворил.**
